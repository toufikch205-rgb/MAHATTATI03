# MAHATTATI03 — دليل تنظيم المشروع

## الهدف
الحفاظ على وظائف التطبيق الحالية مع تحويله تدريجياً إلى بنية مفهومة وسهلة الصيانة. لا تُحذف ملفات التوافق أو تُغيّر أولوية تحميل CSS قبل اختبار الواجهة والوظائف.

## خريطة المشروع الحالية

- `index.html`: نقطة دخول واجهة المستخدم، وما زال يحتوي معظم هيكل HTML الخاص بالتطبيق.
- `admin.html`: نقطة دخول لوحة الإدارة.
- `css/_ordered/`: 85 ملف CSS مستخرج من الأنماط القديمة؛ ترتيبها الحالي مهم جداً للـ cascade.
- `css/repair-layout.css`: طبقة إصلاحات أخيرة للتخطيط والاستجابة للهاتف.
- `css/core/`, `css/layout/`, `css/components/`, `css/pages/`: ملفات CSS دلالية للمراجعة والتنظيم؛ لا تُفعّل نسخها بالتوازي مع ملفات الترتيب القديم إلا بعد مقارنة مرئية.
- `js/core/`: تشغيل التطبيق، الأحداث، التنقل، ومتحكم التوافق القديم.
- `js/features/customer/`: حجز الرحلات، الصفحة الرئيسية للعميل، وسجل الحجوزات.
- `js/features/driver/`: لوحة السائق، واجهة الطلب، التوزيع الحي للرحلات، وواجهة التاجر.
- `js/features/agent/`: تسجيل الوكيل.
- `js/features/admin/`: اعتماد السائقين.
- `js/features/maps/`: منطق الخريطة.
- `js/services/`: الاتصال بقاعدة البيانات وتتبع الجلسة.
- `assets/images/`, `assets/icons/`, `assets/fonts/`: الأصول الثابتة.
- `supabase/` و`tests/`: هيكل تمهيدي فقط؛ لا يُعتبر منطقاً خلفياً أو اختبارات مكتملة.

## ترتيب التحميل الحالي
ملفات JavaScript محمّلة بـ `defer` وبترتيب مقصود. توجد اعتمادات على دوال عامة وأحداث قديمة؛ لذلك لا يُنقل كود بين الملفات اعتماداً على أسماء الملفات وحدها.

## خطة التنظيم الآمنة

### المرحلة 1 — حماية الوضع الحالي
1. الاحتفاظ بترتيب CSS الحالي وملفات التوافق.
2. فحص مسارات الموارد والروابط المحلية.
3. اختبار تسجيل الدخول، العميل، السائق، الوكيل، الإدارة، الخريطة، والقبول الحقيقي للرحلة.

### المرحلة 2 — إكمال CSS الدلالي
1. استخراج قواعد كل مكوّن إلى الملف المناسب.
2. مقارنة قواعد المصدر مع النسخ الدلالية، مع تجنب تفعيل قواعد مكررة.
3. إزالة الملفات الفارغة أو جعلها مسؤولة عن قواعد فعلية فقط بعد التحقق.
4. إبقاء `repair-layout.css` آخر ملف مؤقتاً حتى استقرار التصميم.

### المرحلة 3 — فصل واجهات الصفحات
فصل واجهات تسجيل الدخول والحساب والرحلات والسائق والوكيل إلى ملفات HTML جزئية أو صفحات مستقلة فقط بعد تحديد طريقة التنقل وحالة الجلسة المشتركة. لا تُنقل واجهة منفردة قبل توثيق معرفاتها والأحداث التي تعتمد عليها.

### المرحلة 4 — تفكيك JavaScript
1. رسم خريطة الدوال العامة والمستمعات وترتيب التهيئة.
2. نقل دالة واحدة أو مجموعة مترابطة في كل تغيير.
3. إضافة طبقة توافق عند الحاجة حتى لا تنكسر الأزرار والـ callbacks.
4. تشغيل فحص الصياغة واختبارات تدفق الرحلة بعد كل مجموعة تغييرات.

### المرحلة 5 — التحقق قبل اعتبار المشروع جاهزاً
- لا يُعتبر فحص الصياغة بديلاً عن الاختبار داخل المتصفح.
- يجب اختبار قاعدة البيانات الحقيقية والصلاحيات والتحديثات اللحظية.
- لا تُعلَن الجاهزية النهائية حتى تنجح اختبارات التدفقات الأساسية على الهاتف.

## الوضع الحالي والقيود
هذا الدليل يوثق البنية والخطوات؛ وهو لا يعني أن فصل صفحات HTML أو التفكيك الدلالي الكامل قد اكتمل. حالة النشر النهائي تبقى غير مؤكدة إلى حين تنفيذ اختبارات المتصفح والاتصال بقاعدة البيانات.
